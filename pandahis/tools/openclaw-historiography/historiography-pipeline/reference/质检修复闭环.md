# 质检修复闭环（SSOT）

> 硬门的目的不是「拦住」，而是「诊断 → 定向修复 → 再验」直到通过或明确转线/人审。

## 一、问题

| 旧行为 | 后果 |
|--------|------|
| verify 失败 → `failed` 停住 | 批次卡死（如夏本纪薄君王翻译） |
| 盲重跑整篇 | 不知道改什么，token 空转 |
| 结构错误硬翻 | 永远过不了厚度门 |

## 二、闭环模型（对齐 `hist` 编排器）

```
产出 → verify（硬门）
         ↓ 失败
    failure_classifier（根因 + disposition）
         ↓
    ┌────┴────┬────────────┬──────────────┐
    ↓         ↓            ↓              ↓
 retry_llm  refine_scope  script_fix   route_pipeline
（带反馈）  （局部改）    （规则清洗）  （转朝代补全）
         ↓
    再 verify → 通过 / 熔断 needs_human
```

每条失败落盘 **`{GLBL_id}.repair.json`**（翻译）或 **`qa_state` + verify 产物**（朝代补全），含：

- `root_cause`：如 `THIN_SOURCE`、`COVERAGE_MISS`
- `disposition`：下一步机器可执行动作
- `structured_prompt`：注入下一轮 LLM 的修正说明
- `next_command`：转线时的建议命令

## 三、翻译流水线

| 根因 | disposition | 动作 |
|------|-------------|------|
| 史料 <100 字 | `route_pipeline` | **不调用 LLM**；转朝代知识补全 |
| 必现词/覆盖不足 | `retry_llm` | Phase1/2 带 `format_repair_feedback` 重试 |
| 引入重复 | `refine_scope` | `translate.py refine --scope intro` |
| 归因格式 | `script_fix` | `refine --scope attribution` |
| plan 无效引用 | `retry_llm` | 删 plan 重跑 |

命令：

```bash
python3 translate.py run-one --id GLBL_00043   # 薄源 → rc=2 routed + repair.json
python3 translate.py repair-show --id GLBL_00043
python3 translate.py repair --id GLBL_00043 --execute
```

退出码：`0` 成功 · `1` 可修复失败 · `2` 已转线（非错误）

## 四、朝代知识补全

| 根因 | disposition |
|------|-------------|
| 帝王表缺口 | 注入 mandatory 君王 → fill → compose |
| 详情 verify 失败 | `compose-revise`（带 issues 列表，已有） |
| 重试 ≥3 | `needs_human` |

`gate-renwu` 失败应查看缺失项 → `candidates-renwu` / `compose-detail`，而非整批重跑。

## 五、批次纪律

- 批量脚本：`routed` 与 `ok` 分开统计，**不算 error**
- 同一根因连续失败 ≥3 → 熔断人审，禁止无限循环
- **结构不可修**（薄源、帝王缺口）→ 禁止 LLM 硬翻
